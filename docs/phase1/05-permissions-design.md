# 5. تصميم الصلاحيات: الموظفون والمشاركون

## 5.1 النموذج: RBAC + نطاق تنظيمي + اشتقاق مشاركة

ثلاث طبقات مستقلة، وكل طبقة تضيف حاجزًا لا تتجاوزه الأخرى:

1. **RBAC** (الأدوار والصلاحيات): ماذا يستطيع نوع المستخدم فعلًا (إدارة هيكل، إدارة حسابات، تقارير...).
2. **النطاق التنظيمي** (Scope): أين يُمارس ذلك — عبر `user_role_assignments.institute/branch/department`. لا يوجد نطاق `all_messages`؛ النطاق الأوسع «مركزي/عام» يخص الصلاحيات الإدارية على الهيكل والتشغيل فقط.
3. **اشتقاق مشاركة المحتوى** (Authorization to Read): مُنفصل عن الدور والنطاق تمامًا، ويُحسب فقط من:
   - `correspondence_participants` (to/cc/bcc/forward) أو `conversation_members` الحيّ، أو
   - وجود خطوة اعتماد قائمة مُسندة إليه على المراسلة (المعتمد يقرأ محليًا).

**القاعدة الحاسمة:** لا يوجد أي `permission` ولا أي `role` ولا أي scope يمنح قراءة محتوى لم ينتج عن §5.3. فحص الأمان الثابت (SEC-14) يضمن عدم وجود مسار آخر في الكود.

### قائمة المنع الصريحة (Negative Catalog)

هذه المعرّفات **غير موجودة** ويمنع إنشاؤها، وفحص CI ثابت يفشل الدمج لو ظهرت:

- `view_all_messages` / `view_all_employee_mailboxes` / `view_all_branch_correspondences` / `decrypt_all_messages`
- أي عمود/واجهة «master key» أو «escrow للإدارة»
- صلاحية تجعل BCC أو المشارك المخفي ممكنًا لغير المرسل (انظر 5.5)

## 5.3 من يقرأ مراسلة رسمية؟ (خوارزمية الاشتقاق)

```
can_read(user, correspondence) =
    user ∈ participants(to/cc, أو bcc إن كان هو)  ∧  لم يُزل
 ∨  ∃ forwarding نشط ضمّه صراحةً (added_via=forward) ∧ لم يُزل
 ∨  ∃ approval_request خاص بها ∧ (خطوة حالية/سابقة مُسندة إليه ∨ هو requested_by)
 ∨  هو sender
```

- الإزالة من المشاركين (عند الإحالة) تحدث فقط للمستقبل وتُسجل حدثًا؛ ما فُك تشفيره لا يُسحب (معلن).
- `conversation` بنفس المنطق عبر `conversation_members`.

## 5.4 BCC (قرار معلن بكلفته)

- يُدعم: المرسل يحدد BCC؛ هؤلاء يستلمون غلاف مفتاح ويظهرون في `participants(kind=bcc, hidden_from_others=true)`.
- الخصوصية الوصفية: قائمة BCC تُحذف من استجابات API لغير المرسل ولغير كل BCC؛ في تقارير الإدارة لا يظهر BCC إطلاقًا.
- **التحذير المعلن:** ‏BCC في E2EE يحمي المحتوى ويكشف الحد الأدنى من الوصفية للمستلمين الآخرين (عدد المستلمين قد يدل على وجود مخفيين). إن لم تُحتج فعلًا، ننصح بتعطيله مبدئيًا عبر إعداد نظام.
- مستلم خفي **للمحتوى فقط** (سيلنت ريدر بلا مفتاح) ممنوع — لا يوجد إلا بامتلاك غلاف مفتاح.

## 5.5 أدوار مبدئية (تُفصّل لاحقًا)

| الدور | الصلاحيات | صراحة: لا يشمل |
|-------|-----------|----------------|
| موظف | إرسال/محادثات/أرشفة شخصية/أجهزتي | — |
| رئيس قسم | + تعاميم قسم، موافقات داخل قسمه (حسب مسار) | قراءة بريد مرؤوسيه |
| مدير فرع | + إدارة هيكل فرعه وتقارير وصفية لفرعه | قراءة أي مراسلة موظف |
| مدير معهد | + إدارة معهده وتقاريره | كذلك |
| مدير تنفيذي | + تقارير عبر المعاهد (عدادات) | كذلك |
| Super Admin | إدارة النظام والحسابات والأدوار (بلا `roles.manage` إلا بفصل واجبات) | أي محتوى — مستحيل تقنيًا |
| مسؤول أمن/مراقب | سجل تدقيق، شفافية مفاتيح، تنبيهات أجهزة | محتوى |
| ضابط الأرشيف المؤسسي | طلبات وصول للنسخ المؤسسية المعلنة عبر مسار موافقات | المحتوى الشخصي |

**فصل الواجبات:** من يملك `accounts.manage_users` لا يملك `roles.manage` افتراضيًا؛ ومن يملك `roles.manage` لا يملك `reports` على نفس النطاق بالضرورة — تُضبط لاحقًا في سياسة إسناد.

## 5.6 بيانات الوصفية والتقارير — تخفيف A4/A5/A10

- مدير يطّلع على: عدد المراسلات/المعاملات المكتملة/المتأخرة/متوسط زمن الرد **لوحدته فقط**، دون عناوين أو أطراف محتوى (أطراف الاتصال نفسهم بيانات وصفية: تُعرض مجمعة أو بحد أدنى حسب قرار سياسي معلن — افتراضيًا: تجميع فقط).
- مراقبة أداء النظام: أرقام خدمات، بلا ارتباط بمحتوى.
- أعلى حساسية وصفية (من تواصل مع من ومتى): تُقيّد لمسار التشغيل الفني، ويظهر وصول أي إداري إليها في سجل تدقيق.

## 5.7 نقاط تدقيق إلزامية للمرحلة الثانية من التنفيذ

1. Unit test لكل قاعدة اشتقاق في 5.3 (موجب وسالب لكل فرع).
2. اختبار مسار API كامل: مدير فرع يطلب مراسلة موظفه → 403 في كل نقطة (تفصيل في 07-test-plan SEC-01/02).
3. اختبار وصفية: التقارير لا تعيد أسماء أطراف ولا عناوين (SEC-12 فكرة القريبة).
4. فحص CI ثابت على قائمة المنع في 5.2.
