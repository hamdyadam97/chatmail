# 7. خطة اختبار التشفير والخصوصية

مبدأ عام: الاختبارات الوظيفية لا تغني عن مراجعة أمنية مستقلة قبل الإنتاج (موثقة في خطة النشر). لكل اختبار: المعرف، الهدف، طريقة التنفيذ، وبوابة النجاح.

## 7.1 الـ 18 اختبارًا الإلزامية (من المتطلبات)

| المعرف | الاختبار | التنفيذ |
|--------|----------|----------|
| SEC-01 | مدير الفرع لا يقرأ رسائل الموظفين الخاصة | API tests: مدير فرع يستدعي تفاصيل مراسلة/محادثة موظفه → 403 في كل نقطة (list, retrieve, WS subscribe, attachments, replies) |
| SEC-02 | Super Admin لا يقرأ المحتوى من API | نفس الحزمة بصلاحية sysadmin كاملة + فحص استجابات لا تعيد ciphertext إلا لجهاز مشارك |
| SEC-03 | DBA لا يستخرج النص من المخزن وحده | فحص لقطة DB: بحث Greppable عن نصوص معروفة/توقيعات خوارزميات/مفاتيح PEM → صفر نتائج؛ + اختبار «DB only» يحاول فك أي ciphertext دون أسرار |
| SEC-04 | استبدال المفتاح العام غير المصرح يُكتشف أو يُمنع | حقن device key مزيف عبر API مباشر (تجاوز عميل) → رفض بسبب فشل توقيع سلسلة الثقة؛ تعديل مفتاح موجود في DB → كسر سلسلة الشفافية يُكتشف عند فحص المستخدم وأداة التدقيق |
| SEC-05 | فقدان جهاز لا يكشف أجهزة/محادثات أخرى | إجراء إبطال لجهاز واحد ثم محاولة فك رسائل محادثات لم يكن طرفًا فيها بمفاتيح الجهاز المسحوبة → فشل؛ والجهاز المُبطل لا يفك رسائل الأجيال اللاحقة |
| SEC-06 | إزالة عضو من جروب تمنعه من الأجيال المستقبلية | سيناريو MLS: remove → محاولة فك epoch لاحق بأسراره القديمة → فشل تشفيري فعلي (لا مجرد رفض API) |
| SEC-07 | جهاز جديد لا يكشف التاريخ تلقائيًا | إضافة جهاز معتمد → لا يوجد Welcome للأجيال السابقة → استرجاع رسالة قديمة يفشل حتى بلا مانع API |
| SEC-08 | استعادة كلمة المرور لا تكشف مفاتيح التشفير | مسار reset كامل → التحقق: لا تغير في user_crypto_identities/trusted_devices، والمستخدم يدخل بجهازه المعتاد كما كان؛ ولا توجد أي قدرة إدارية تلمس crypto |
| SEC-09 | لا مفاتيح خاصة في قاعدة البيانات | فحص مخطط CI ثابت + فحص محتوى: كشف تلقائي لأيام PEM/RAW بأطوال مفاتيح خاصة/أسرار 32+ بايت في أعمدة غير مصرح بها → صفر |
| SEC-10 | لا محتوى غير مشفر في السجلات | تشغيل سيناريوهات مراسلات مع canary strings في النصوص → جمع logs (app, db, redis, nginx) → لا يوجد أي canary نصي؛ اختبار أخطاء مصطنعة تتسرب payload → مطهر السجلات يقص |
| SEC-11 | الإشعارات لا تسرّب المحتوى | إنشاء رسائل بعناوين فريدة → جمع notifications/outbox/WS events → يتحقق من غياب أي canary ووجود نص عام فقط |
| SEC-12 | البحث لا يسرّب محتوى | بحث السيرفر (وصفية) بمصطلحات من داخل نصوص مشفرة → لا نتائج؛ بحث عميل محلي يعمل فقط على نصوص مفكوكة للمستخدم نفسه |
| SEC-13 | منع تنزيل مرفقات غير مصرح بها | مستخدم خارج المشاركة يطلب blob أو envelope أو stored_file key → 403 في كل المسارات (مباشر، presigned، تخمين معرف) |
| SEC-14 | لا صلاحية إدارية تتجاوز E2EE | فحص CI ثابت: لا وجود لمعرّفات Negative Catalog؛ + اختبار مسارات يدوية: أي endpoint جديد يمر بنفس object-permission gate |
| SEC-15 | منع Replay وفق البروتوكول | إعادة إرسال ciphertext سابق داخل المحادثة → MLS message protection يرفض/يُعلّم؛ وإعادة استخدام KeyPackage مستهلكة → رفض (consumed_at) |
| SEC-16 | عدم فقدان الرسائل عند انقطاع مؤقت | chaos test: فصل WS أثناء تدفق رسائل → إعادة الاتصال → استرجاع كامل بالترتيب (seq) دون تكرار |
| SEC-17 | سلامة الرسائل أثناء النقل | تعديل byte واحد في ciphertext (في layer اختبار، ليس MITM حقيقي) → فك التشفير يفشل بوضوح للمستخدم لا بصمت |
| SEC-18 | عدم تسريب المفاتيح من نسخ احتياطية غير مشفرة | فحص كل وسائط النسخ (DB dumps, storage snapshots, redis dumps) بنفس منهج SEC-03 + التحقق أن key backups المخزنة لا يمكن فكها دون recovery key |

## 7.2 اختبارات تشفير إضافية

| الفئة | الاختبار |
|-------|----------|
| متجهات معيارية | تشغيل vector suites الرسمية للمكتبة المختارة (MLS RFC 9420 vectors عبر mls-rs؛ وبدائلها عند fallback) |
| خصائص (Property) | توليد عشوائي: أي عضوية/تسلسل تغييرات عضوية → الأسرار تتطابق فقط لدى الأعضاء الحاليين (pytest + hypothesis على طبقة Rust/WASM عبر Node runner) |
| الاستعادة | round-trip: backup → restore على جهاز جديد → إمكانية فك الأجيال الحية واستمرار المحادثات؛ + فشل استعادة بمفتاح خاطئ → رسالة واضحة بلا تسريب |
| الشفافية | tamper في أي حدث وسيط → كشف عند إعادة الحساب؛ انقطاع السلسلة → إنذار |
| توقيع القرارات | تعديل أي حقل في decision_payload → فشل التحقق من التوقيع |
| الأداء | زمن Commit لمجموعة 100 جهاز؛ استهلاك ذاكرة WASM في تبويب خامل؛ رسائل/ثانية في قناة نشطة (1000 رسالة) |
| ترقية الخوارزمية | محاكاة نشر version جديد من algorithm/payload version: قراءة قديم + كتابة جديد دون فقدان |

## 7.3 بوابات الجودة حسب المرحلة

1. **نهاية بناء الحسابات/الهيكل (قبل المراسلات):** كل اختبارات RBAC/scope سالبة وموجبة خضراء، SEC-01/02/08/14 على مستوى الهيكل، MFA وتغيير كلمة المرور، فصل reset-password عن أي crypto hook (حتى لو crypto لم يُبنَ بعد — نثبت العزل الآن).
2. **نهاية Spike التشفير:** بنود Spike الأربعة في 02-protocol-comparison.md + SEC-05/06/07/15/17 على نموذج صغير.
3. **قبل Pilot:** الـ 18 كاملة خضراء + اختبارات §7.2 الأساسية + تشغيل chaos/reconnect + مراجعة أمنية مستقلة موثقة.
4. **CI دائم:** حزمة SEC-01..18 في كل دمج (أو ليليًا للثقيلة منها) + فحوصات التسرب الثابتة (SEC-09/10/14) في كل build.

## 7.4 أدوات مقترحة

pytest + pytest-django + hypothesis (backend) · Node test runner للـ WASM suites · Playwright لسيناريوهات end-to-end الأساسية (بلا crypto ثقيل في كل run) · canary/logger fixtures مخصصة لـ SEC-10 · فحص schema/محتوى DB لـ SEC-03/09 كـ pytest markers منفصلة.
