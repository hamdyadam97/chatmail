## الملخص التنفيذي للقرارات

1. **البروتوكول:** MLS ‏(RFC 9420) عبر مكتبة `mls-rs` مُصرّفة إلى WASM داخل المتصفح، وDjango يعمل كـ Delivery Service ودليل مفاتيح فقط. البديل الاحتياطي: ‏Matrix Olm/Megolm (vodozemac). التفاصيل والمبررات في الملف 02، مع Spike تحقق قبل الالتزام الكامل.
2. **قاعدة خصوصية غير قابلة للتجاوز:** لا يوجد أي دور أو صلاحية تمنح قراءة محتوى مراسلة موظف آخر. القراءة مشتقة حصرًا من جدول المشاركين. لا Master Key، لا Backdoor.
3. **الأرشيف المؤسسي:** نسخة مشفرة صريحة لمستلم مؤسسي معلن، تُنشأ عند الإرسال فقط للمراسلات المصنفة «رسمي — قابلة للأرشفة المؤسسية»، والمرسل يرى هوية المستلم المؤسسي قبل الإرسال. ليست بابًا خلفيًا.
4. **الاستعادة:** Recovery Key محلي (256-bit) يغلّف حزمة مفاتيح مشفرة تُرفع اختياريًا للسيرفر؛ السيرفر لا يملك أبدًا مفتاح الاستعادة أو المفاتيح الخاصة. فقدان الأجهزة + مفتاح الاستعادة = هوية جديدة وفقدان المحتوى القديم (معلن للمستخدم).

## نقاط تحتاج قرارك قبل الاعتماد

1. اعتماد قرار البروتوكول (MLS أولًا مع Spike، أو الانتقال مباشرة لبديل Matrix).
2. دعم BCC في المراسلات (مدعوم بتصميم «مشارك مخفي» — له كلفة تعقيد وقيود بيانات وصفية موثقة).
3. نطاق سياسة الأرشفة المؤسسية: هل تُطبق على كل المراسلات الرسمية تلقائيًا أم بتصنيف صريح من المرسل؟
4. هل إعداد التشفير إلزامي لجميع الموظفين من اليوم الأول أم تفعيل تدريجي؟
5. بيئة الاستضافة: On-prem بالكامل (معهدك/سيرفر المجموعة) أم سحابة؟ (تؤثر على KMS للبيانات غير E2EE وعلى النسخ الاحتياطي).

## ما بعد الاعتماد

بناء الحسابات المستقلة + الهيكل التنظيمي + المصادقة وMFA + RBAC مع اختبارات حقيقية، ثم Spike تشفير MLS في المتصفح، ولا نبدأ المراسلات المشفرة قبل اجتيازه.
