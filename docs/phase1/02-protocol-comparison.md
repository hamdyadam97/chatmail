# 2. مقارنة بروتوكولات E2EE وقرار الاختيار

## 2.1 معايير التقييم (مشتقة من المتطلبات)

1. دعم متعدد الأجهزة لكل مستخدم (كل جهاز مفتاح مستقل).
2. مراسلة غير متزامنة (مستلم غير متصل).
3. محادثات جماعية مع تغيير عضوية (إضافة/إزالة) وتحديث مفاتيح.
4. نضج مكتبة تعمل في المتصفح (WASM/JS) ومراجعات أمنية.
5. السيرفر «أنبوب غبي»: يخزن ciphertext وحزم مفاتيح عامة فقط.
6. ضمانات موثقة: Forward Secrecy / Post-Compromise Security / منع Replay — دون ادعاءات زائدة.
7. قابلية ربط الهوية التشفيرية بهوية الموظف والتحقق من الأجهزة.
8. جهد التكامل مع Django/React وقابلية الصيانة طويلة المدى.

## 2.2 جدول المقارنة

| المعيار | Signal Protocol (libsignal) | Matrix: Olm + Megolm (vodozemac) | MLS ‏RFC 9420 (mls-rs / OpenMLS) |
|---------|------------------------------|----------------------------------|----------------------------------|
| أصل التشفير 1:1 | Double Ratchet (مرجعي) | Olm (Double Ratchet) | مجموعة MLS من عضوين (Commit-driven) |
| الجماعي | Sender Keys (توزيع عبر سيرفر) | Megolm: جلسة مجموعة تُوزع pairwise عبر Olm | أصلي في البروتوكول: شجرة أسرار، إضافة/إزالة بـ Add/Remove proposals |
| متعدد الأجهزة | نعم (linked devices) | نعم (كل جهاز client مستقل) — ناضج جدًا في Element Web | نعم (كل جهاز Leaf مستقل باعتماده) |
| غير متزامن | نعم (PreKey bundles) | نعم (Key bundles + تشارك لاحق) | نعم (KeyPackages مخزنة، Welcome/Commit مخزنة للمستلمين غير المتصلين) |
| FS / PCS | الأقوى: FS لكل رسالة | Megolm لا يعطي FS لكل رسالة داخل الجلسة؛ يُدار بالتدوير + Olm | FS على مستوى Epoch؛ PCS حقيقي عند كل Commit (إزالة/تدوير) |
| إزالة عضو | يدوي (إعادة توزيع Sender Key) | تدوير جلسة Megolm جديدة — عملي لكن تدريجي | إزالة تشفيرية أصلية: العضو المُزال لا يقدر على حساب أسرار الأجيال التالية |
| مكتبة Web | رسميًا Node/JNI/Swift؛ المتصفح غير مدعوم رسميًا، المكتبات المجتمعية قديمة غير مدعومة | ناضج جدًا: ‏matrix-rust-sdk-crypto-wasm يعمل في Element Web اليوم | ‏mls-rs (Rust) يُصرّف WASM؛ OpenMLS يدعم WASM جزئيًا. أقل نضجًا في المتصفح |
| دور السيرفر | دليل مفاتيح + تمرير رسائل | يقلّد homeserver: ‏/keys/query‏ /keys/claim‏ to-device | Delivery Service نقي: KeyPackages + تخزين Commit/Welcome/Application — أقرب لنموذج «الأنبوب الغبي» |
| مراجعة/تدقيق | واسع لكن المكتبة الموزعة محدودة | vodozemac مراجعة واسعة، مستخدمة على نطاق ضخم | معيار IETF، RFC 9420، مراجعات وتحليلات عديدة؛ mls-rs مستخدم من AWS |
| التكامل مع Django | يحتاج بناء طبقة توزيع مفاتيح خاصة كاملة | يحتاج محاكاة endpoints Matrix أو قيادة المكتبة خارج نموذجها (هشاشة) | نبني فقط الخدمات: تخزين KeyPackages، تمرير رسائل، دليل هويات + شفافية |
| ملاءمة لمراسلات + موافقات + أرشفة | جيدة | جيدة | جيدة، وتوقيع/اعتماد اقتراحات يناسب سجل الموافقات الموقع |

## 2.3 خيارات مرفوضة (مبررات)

- **PGP/S/MIME للرسائل:** لا FS، لا سرية مستقبلية، تجربة أجهزة سيئة — مرفوض.
- **«تجميعنا الخاص» (AES-GCM + ECDH يدويًا):** ممنوع صراحة في المتطلبات؛ سبب النجاة: إدارة الجلسات والتجديد والعضوية وReplay تُبنى بالدماء. مرفوض.
- **B impelemntation على خادم الإدارة:** أي Key Escrow للإدارة — مرفوض بموجب قاعدة الخصوصية.

## 2.4 القرار

**البروتوكول المعتمد: MLS (RFC 9420)** — كل محادثة (ثنائية أو جماعية أو قناة أو «خيط مراسلة») هي مجموعة MLS واحدة. الجهاز في المتصفح/تطبيق الجوال يشغّل `mls-rs` عبر WASM؛ Django يقدم فقط: دليل الهويات والأجهزة، تخزين KeyPackages، تمرير رسائل MLS المشفرة (Commit/Welcome/Application)، وخدمة الشفافية.

### لماذا MLS وليس غيره؟

1. **إزالة العضوية والأجهزة أصلية:** شرطك الصريح «إزالة موظف من الجروب تمنعه من فك تشفير الرسائل المستقبلية» يأتي من قلب البروتوكول (Remove proposal يقصّ العضو من الشجرة)، وليس كحلولة إضافية هشة فوقه.
2. **نموذج السيرفر مطابق لمتطلبك:** ‏MLS يفصل صراحة بين State (عند العملاء) وDelivery Service (عند السيرفر). هذا أدق تطابق مع «Django يوجّه البيانات المشفرة فقط».
3. **سرية مستقبلية بعد الاختراق (PCS):** أي Commit بعد اختراق جهاز يعيد توليد الأسرار — يخدم سيناريوهات A7/A6.
4. **معيار IETF قابل للتدقيق والاستمرارية**، بدل قفل مورده في بروتوكول مملوك أو مشروع واحد.
5. **توقيع Commit/Proposal بالاعتماديات (Credentials):** يسمح بربط كل جهاز بسلسلة ثقة موثقة (هوية المستخدم توقّع جهازه) — وهو أساس Key Transparency والتحقق من الأجهزة عندنا.

### الضمانات الفعلية — بصدق ودون مبالغة

| الضمان | الحالة في MLS عندنا |
|--------|---------------------|
| سرية المحتوى من السيرفر | كاملة (المحتوى ciphertext، والمفاتيح لدى الأجهزة فقط) |
| سلامة ومصادقة الرسائل ومنع Replay | مدمجة في بروتوكول الرسائل (توقيع + حماية إعادة تشغيل ضمن المجموعة) |
| Forward Secrecy | على مستوى Epoch: اختراق مفتاح عضو/جهاز لا يكشف أجيالًا سابقة؛ داخل نفس الـ Epoch لا يوجد FS لكل رسالة في MLS |
| Post-Compromise Security | عند كل Commit بعد الحادثة (سياسة: Commit عند كل تغيير عضوية/جهاز، وCommit دوري عند نشاط متواصل) |
| منع حقن جهاز وهمي | اعتماد الأجهزة + سلسلة ثقة الهوية + شفافية المفاتيح (لا يأتي من MLS وحده) |

سياسة التشغيل المعتمدة لسد فجوة FS داخل الـ Epoch: **Commit جديد بعد كل N رسائل (N=50 افتراضيًا، قابل للضبط) أو عند أي عودة اتصال بعد غياب طويل** — مع إعلان المستخدم أن «حذف فوري» لكل رسالة بعد كل إرسال ليس ضمانًا في MLS.

## 2.5 خطة تحقق (Spike إلزامي قبل بناء المراسلات)

قبل كتابة مكونات التشفير الفعلية، Spike مدته حتى أسبوعان يثبت في المتصفح:

1. بناء `mls-rs` كـ WASM، تخزين حالة المجموعة في IndexedDB، إنشاء مجموعة من 2 و50 عضوًا.
2. إرسال/استقبال غير متزامن عبر Django (Commit/Welcome مخزنة حتى الاتصال).
3. Add/Remove عضو وإبطال جهاز والتحقق من فشل فك تشفير الأجيال اللاحقة للمُزال.
4. الأداء: زمن إنشاء Commit لمجموعة 100 جهاز، وحجم الحالة.
5. اختبار أحمال WASM في علامة تبويب خاملة (لا استنزاف للبطارية/الذاكرة).

**معيار النجاح:** اجتياز البنود 1–4 ضمن حدود أداء مقبولة موثقة.
**خطة الاحتياط:** عند الفشل، الانتقال إلى Matrix vodozemac عبر `matrix-rust-sdk-crypto-wasm` مع Django يقلّد الحد الأدنى من نقاط Matrix للمفاتيح والتوجيه — نفس نموذج الأمان، بمكتبة أنضج في المتصفح وأقل نضجًا في إزالة العضوية (تُدار بتدوير Megolm عند كل تغيير عضوية).

## 2.6 ما يبقى ثابتًا مهما كان الاختيار

- الهوية التشفيرية للمستخدم والأجهزة وسلسلة الثقة والشفافية وRecovery — كلها فوق البروتوكول ولا تتغير.
- قاعدة «السيرفر لا يرى Plaintext أبدًا» لا تتغير.
- واجهة التخزين المشفرة على العميل (IndexedDB مشفر، لا localStorage) لا تتغير.
