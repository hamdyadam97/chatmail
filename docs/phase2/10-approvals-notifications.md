# 10. الموافقات والإشعارات (المرحلة الرابعة — الشريحة الأولى)

## 10.1 الموافقات

**المبدأ:** محرك الموافقات لا يضيف أي مسار قراءة. كل معتمد يجب أن يكون **مستلمًا (إلى/نسخة) للمراسلة** فيقرأ محتواها عبر مجموعة MLS لخيطها كأي مستلم. إن حدد المرسل (أو مسار معرّف) معتمدًا من خارج المستلمين يرفض الخادم ويعيد قائمتهم في `not_participants` — على المرسل إرسال المراسلة لهم أو إحالتها أولًا، بشكل ظاهر لكل الأطراف.

| العنصر | السلوك |
|--------|--------|
| من يطلب | مرسل مراسلة مُرسلة (غير مغلقة)؛ طلب قائم واحد لكل مراسلة (UNIQUE جزئي) |
| الخطوات | متسلسلة (حتى 10)؛ كل خطوة `all` (اعتماد الجميع) أو `any` (يكفي واحد) — حتى 20 معتمدًا |
| القرارات | `approved` / `rejected` / `returned`؛ الرفض أو الإعادة ينهي الطلب ويُلغي الخطوات اللاحقة |
| الحالات | pending ← approved ← completed (يعلّمها مقدّم الطلب)، أو rejected / returned / cancelled |
| منع التكرار | خانة كل معتمد في الخطوة تُملأ مرة واحدة: `UNIQUE(step, slot_user)` + فحص الخدمة |
| التفويض المؤقت | ≤ 90 يومًا، قابل للإلغاء؛ ينقل صلاحية القرار فقط — المفوَّض يجب أن يكون مستلمًا للمراسلة بنفسه؛ القرار يسجّل الخانة والمنفّذ والتفويض |
| المسارات المعرّفة | `approvals.define` في نطاق الوحدة؛ محدِّدات `{user}` أو `{role, scope: sender_institute/branch/department}`؛ تُلتقط لقطة الخطوات عند إنشاء الطلب |
| الرؤية | أطراف المراسلة فقط (نفس بوابة القراءة)؛ مدير الفرع وsys_admin ← 403 |

### توقيع القرار

الحمولة JSON قانونية (مفاتيح مرتبة، بلا مسافات، ASCII):

```
{approver_id, content_hash, correspondence_id, decided_at, decision, device_id, on_behalf_of, request_id, step_order}
```

- `content_hash` = SHA-256 للـciphertext (رسالة MLS) الذي فكّه المعتمد فعلًا — العميل يحسبه بنفسه ويرفض التوقيع إن خالف بصمة الطلب.
- التوقيع Ed25519 بمفتاح **جهاز** المعتمد فوق `"corr-approval-decision-v1\n" ‖ payload`. الخادم يتحقق بالمفتاح العام للجهاز (`trusted_devices.identity_sign_pub`)، ويشترط جهازًا نشطًا للمستخدم نفسه، وتطابق كل حقل مع الطلب، وفرق وقت ≤ 10 دقائق.
- الحمولة والتوقيع يُخزنان كما هما، وأي مشارك يعيد التحقق منهما محليًا بمفتاح الجهاز من الدليل (الواجهة تعرض «توقيع صحيح»/«غير صالح»).
- مفتاح الجهاز نفسه يوقّع في MLS؛ فصل السياق (وسم MLS مقابل `SIGNING_CONTEXT`) يمنع صلاحية توقيع أحدهما للآخر.

**تنبيه معلن:** هذا توقيع سلامة تشفيري يثبت مَن قرر وعلى أي نسخة داخل النظام، **وليس توقيعًا إلكترونيًا نظاميًا معتمدًا قانونيًا**.

**الملاحظات على القرار** لا تُخزن على الخادم كنص؛ تُرسل ردًّا مشفّرًا في خيط المراسلة.

## 10.2 الإشعارات

- جدول `notifications` + `notification_preferences` (كتم أنواع عن الدفع الحي).
- `notify(users, kind, ref)` لا يقبل أي نص: العنوان من قائمة ثابتة لكل نوع (SEC-11).
- الأنواع: مراسلة جديدة / رد / إحالة، طلب اعتماد، قرار اعتماد، تنبيه أجهزة (إضافة/اعتماد/إبطال جهاز — §6: إخطار المستخدم على أجهزته).
- الدفع الحي بعد إتمام المعاملة (`on_commit`) عبر `/ws/notifications/` (و`/ws/correspondences/` = نفس البث مصفّى لأنواع المراسلات) بتذكرة لمرة واحدة. الواجهة: جرس بعدّاد واتصال واحد بإعادة اتصال أسّية، وصفحة الإشعارات.

## 10.3 حدود معلنة

- لا Celery/outbox بعد: الدفع متزامن بعد الالتزام؛ إشعار يفوته عميل غير متصل يبقى في الجدول ويُجلب عند الاتصال (لا فقد)، لكن لا إعادة محاولة لقنوات خارجية (بريد/جوال) لأنها غير مبنية.
- لا تذكير تلقائي عند تجاوز مهلة خطوة (`timeout_hours` مخزن فقط) — يحتاج مجدولًا (Celery beat).
- المعتمد يجب أن يكون مستلمًا؛ لا «معتمد مخفي» يقرأ دون علم الأطراف — مقصود.
- التعاميم والأرشفة المؤسسية والتقارير لم تُبنَ بعد.
