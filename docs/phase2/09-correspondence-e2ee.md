# 9. المراسلات الرسمية المشفرة (المرحلة الثانية — الشريحة الأولى)

يبني هذا المستند على `03-key-management.md` §3.4 («كل خيط مراسلة رسمي = مجموعة MLS») و`05-permissions-design.md` §5.3. لا يضيف خوارزمية جديدة: المحتوى يُحمى بـ MLS (mls-rs) كما في الشات، والمرفقات بـ AES-256-GCM عبر WebCrypto.

## 9.1 النموذج

| العنصر | أين يعيش | ما يراه الخادم |
|--------|----------|----------------|
| خيط المراسلة | `Conversation(type=correspondence)` = مجموعة MLS واحدة (المرسل + إلى + نسخة) | المعرّف، الجيل، الأعضاء |
| المحتوى (العنوان + النص + أسماء المرفقات ومفاتيحها + الاقتباس المحال) | رسالة MLS تطبيقية واحدة (`correspondences.content_message`) | ciphertext فقط |
| المرفق | blob = ‏IV(12) ‖ AES-256-GCM(ciphertext+tag)، AAD ثابت | الحجم وSHA-256 فقط |
| الرقم المرجعي، الأولوية، التصنيف، الاستحقاق، الحالة، المستلمون | `correspondences` / `correspondence_participants` | بيانات وصفية صريحة (مقصودة) |

صيغة المحتوى (الإصدار 1): `{v, kind, correspondence_id | reply_to_id, subject, body, attachments[{id, name, mime, size, key, sha256}], forwarded?}` — `frontend/src/features/correspondence/content.ts`.

## 9.2 التدفقات

1. **إرسال جديد:** تشفير المرفقات ورفع الـciphertext ← `POST /correspondences/` (صف `draft` + خيط) ← بناء المجموعة على العميل: Welcome لكل جهاز نشط للمستلمين ولأجهزة المرسل الأخرى، ثم Commit ← تشفير المحتوى ← `POST /correspondences/{id}/send/` يخزن رسالة MLS ويربط المرفقات ويُصدر الرقم المرجعي داخل قفل صف (`reference_sequences`، صيغة `{معهد}-{فرع}-{سنة}-{تسلسل:06}`) ويجمّد الصف.
2. **الرد:** `POST /correspondences/{id}/reply/` في الخيط نفسه (نفس المجموعة) — يصل لكل أطراف الخيط (رد على الجميع). الرد لمجموعة جزئية = مراسلة جديدة.
3. **الإحالة:** `POST /correspondences/{id}/forward/` يفتح **خيطًا جديدًا**؛ المُحيل يفك الأصل محليًا ويعيد تشفير ما يحيله (مع مفاتيح المرفقات) للمستلمين الجدد. المستلم الجديد لا ينضم لخيط الأصل فلا يرى ردوده ولا يستطيع تشفيريًا فك محتواه.
4. **الفتح:** فك MLS لمرة واحدة، لذا يُغذّى الخيط كاملًا بالترتيب ويُخزن كل محتوى مفكوك مغلّفًا بالـKEK في IndexedDB (مخزن `mail`) بمفتاح (الخيط، seq) ثم يُربط بالصف.

## 9.3 الضمانات الفعلية

| الضمان | الآلية | الدليل |
|--------|--------|--------|
| الخادم/المسؤول/DBA لا يقرأ المحتوى | ciphertext فقط في DB وفي التخزين | e2e: صفر canary في ملف SQLite وفي blobs (SEC-03) |
| مدير الفرع وsys_admin لا يصلان | بوابة مشاركين واحدة لكل endpoint؛ 403 موحد للمعرّف المجهول والممنوع | `test_correspondence_security.py` (SEC-01/02) + e2e |
| رفض النص الصريح | `mls_payload` يجب أن يكون ثنائيًا؛ blobs بصيغ ملفات معروفة أو UTF-8 تُرفض | اختبارات + e2e |
| عدم التعديل بعد الإرسال | لا PUT/PATCH؛ حارس `save()`/`delete()` في النموذج؛ CHECK في DB | `test_sent_correspondence_is_immutable` |
| رقم مرجعي بلا تكرار | قفل صف + UNIQUE | اختبارات التسلسل لكل معهد |
| نسبة المحتوى لمرسله | العميل يطابق `sender_index` الموثّق في MLS مع (المستخدم، الجهاز) الذي يدّعيه الخادم، ويتحقق من ربط المحتوى بالصف | e2e + تحذير أحمر في الواجهة |
| سلامة المرفق | SHA-256 داخل المحتوى المشفّر + GCM | e2e (SEC-17) |
| التنزيل مقيد بالمشاركة | الرفع للمالك حتى الربط؛ بعده لقُرّاء أي مراسلة مربوطة؛ امتلاك الـblob بلا مفتاح لا يفيد | SEC-13 |
| عضوية الخيط ثابتة | الخادم يرفض إضافة/إزالة أعضاء أو Commit يضيف غير الأعضاء؛ والمحتوى لا يدخل إلا عبر `/send/` | اختبارات |

## 9.4 حدود معلنة (لا ندّعي غيرها)

- **BCC غير مبني:** قائمة أعضاء مجموعة MLS مرئية لكل الأعضاء، فلا يمكن إخفاء مستلم داخل المجموعة نفسها. البناء الصحيح = خيط مستقل لكل مستلم مخفي. حتى ذلك يرفض الخادم `bcc_user_ids` (والإعداد `CORRESPONDENCE_BCC_ENABLED` معطّل).
- **المسودات محلية على الجهاز** (مشفّرة بالـKEK) ولا تتزامن بين الأجهزة، ولا تحفظ المرفقات.
- **جهاز يُضاف لاحقًا** لا يرى ما أُرسل قبل إضافته في الخيط (SEC-07)، والواجهة تقول ذلك صراحة.
- **مسح المخزن المحلي** يُفقد نسخة المحتوى المرسل من هذا الجهاز (MLS لا يفك رسائل الجهاز نفسه)؛ المستلمون غير متأثرين. النسخ الاحتياطي المشفّر لهذا المخزن مرحلة لاحقة.
- **الرد يكشف للخادم** من رد على من (بيانات وصفية) — مثل أي نظام صادر/وارد.
- **تصنيف «قابلة للأرشفة المؤسسية»** علامة وصفية فقط حاليًا؛ لا تُنشأ نسخة مؤسسية ولا يحصل أي طرف على مفتاح.
- **فحص البرمجيات الضارة** غير ممكن على الخادم لمحتوى E2EE؛ الواجهة تنبه المستخدم للفحص محليًا.
- **إشعارات فورية للمراسلات** (`/ws/correspondences/`) لم تُبنَ؛ الواجهة تستطلع كل 20 ثانية.
- الاختبارات لا تغني عن مراجعة أمنية مستقلة قبل الإنتاج.

## 9.5 التشغيل والاختبار

```bash
.venv/Scripts/python.exe -m pytest backend/tests -q              # 196 اختبارًا
sh frontend/scripts/run-e2e-fresh.sh e2e-correspondence.mjs        # 49/49 على قاعدة مؤقتة
```

`run-e2e-fresh.sh` ينشئ قاعدة مؤقتة لكل تشغيل: سكربتات e2e تولّد هويات جديدة لحسابات seed_demo، وعلى قاعدة مستعملة يرفض الخادم — بحق — اعتماد جهاز جديد دون جهاز موثّق.
